# Modal & Async Infrastructure

- **Long-Running Tasks:** Any process taking >60s (like multi-row syncs) must be refactored to a background task using `modal.spawn()`. Do not run inside a synchronous web request.
- **Responsive UI:** Instant feedback ("Sync started") is required before launching background work.
- **Web endpoints:** Use `@modal.fastapi_endpoint`. No standalone Flask/FastAPI servers — Modal handles hosting and containerization.
- **Architecture pattern:** Cloudflare Worker (entry, routing, static HTML) → Modal Python function (Python work, LLM calls, scraping). Never the reverse.
- **Persistent state:** Use `modal.Volume` for any file that must survive cold starts (SQLite DBs, JSON caches). Files written outside a Volume are wiped per invocation.
- **Secrets:** Stored as Modal secrets (`modal secret create <name>`) and injected via `secrets=[modal.Secret.from_name("<name>")]`. Never hardcode in source.
- **`modal secret create --force` replaces the entire secret** — any key not explicitly passed is permanently deleted. To add or update a single key in an existing secret: use the Modal dashboard (modal.com → Secrets → [name] → Edit). Only use `--force` from the CLI when rebuilding from scratch with all values sourced from `.env` in the same command.
- **Never use random-generated fallbacks for stable secrets** (session keys, HMAC keys, signing secrets). A `secrets.token_hex(32)` fallback invalidates all active sessions on every cold start. Hard-fail with `os.environ["KEY"]` — it forces proper configuration and surfaces the missing secret at deploy time, not at user login time.
- **Deployment safety:** Before `modal deploy`, confirm `pwd` is the mainline project root — not a worktree (`~/.claude/worktrees/...`). Deploying from a stale worktree silently rolls back recently merged changes in production with no error or warning.
- **Worktree fixes must land in mainline before the session ends.** Fixes applied in a worktree are invisible to other sessions working on mainline. If two Claude Code sessions run concurrently — one in a worktree, one on mainline — the mainline session wins and silently reverts the worktree's changes. For any hotfix to a live bug: either apply directly to mainline, or merge the worktree before closing the session.
- **PRs are mandatory for any change inside `app/`, `requirements.txt`, or any config file** (`app/config.py`, `wrangler.toml`, `.env.example`, etc.). Branch → commit → push → open PR → merge. This is a lifecycle discipline, not a code-review gate (solo work). The point: every change to application code or its dependency/config surface passes through a tracked branch + PR so stranded uncommitted work surfaces immediately instead of silently rotting in a working tree. Non-`app/` changes (memory files, HANDOFF.md, design references, lessons_learned) can land directly on main when convenient. Reference incident: 2026-05-17 recruiting-engine — a `User Guide` page sat uncommitted on main through several sessions because no PR forced it through the lifecycle; recovery required archaeology across worktrees and stash trees. Reference incident: 2026-05-25 recruiting-engine — Firecrawl changes to `app/config.py`, `app/sheets/sync.py`, and `requirements.txt` were committed directly to main, violating this rule; retroactively fixed via PR #26.
- **Two concurrent Claude Code sessions require deploy coordination.** When two sessions run against the same repo simultaneously, only one session owns `modal deploy` at any given time. The non-deploying session must `git stash && git pull --rebase origin main && git stash pop` before attempting any commit or deploy — repeated diverging-branch conflicts are the symptom of missing this. Communicate ownership via HANDOFF.md or direct session notes before deploying.
- **Starlette/FastAPI route collisions fail silently.** When two `Route()` entries or `@app.route` decorators match the same path pattern, the framework matches the first registered handler with no warning at startup and no error at runtime — the second handler never runs and the wrong handler returns an unexpected 400 or 422. Before adding any new route, `grep` the full path string across all route registrations in the file. Applies equally to Starlette `Router` and FastAPI `APIRouter`.
- **Batch scripts must mirror their live Modal route counterparts.** When a local batch script (`batch_*.py`) replicates the logic of a Modal route (same prompt, same data fetching), they must stay in sync. When adding prompt improvements, fundamentals injection, or capability upgrades to a route, update any companion batch scripts in the same session. Divergence is silent — the batch script produces degraded results (e.g., hallucinated values from training data) while the live app works correctly.
